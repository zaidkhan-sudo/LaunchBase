From a repo URL to a running container.

LaunchBase clones a GitHub repository, containerizes it, ships the image to AWS, and streams every line of the build to the browser as it happens. This document traces that path end to end, through both processes that make it work.

01 — Topology

Two processes that never import each other

A docker build can take minutes and saturate a core. Run it inside the API process and it blocks the event loop, stalling every other request. So the build lives in its own process. The price of that split is that the worker has no access to the Socket.IO server, which is the exact problem the streaming layer solves.

Why the Docker CLI, not a Docker SDK

child_process.spawn hands back raw stdout and stderr chunks. Those go straight into the logger, which is what makes live build output cheap to implement.

Middleware order is load-bearing

First, so a preflight OPTIONS short-circuits before body parsing. credentials:true is what lets the httpOnly refresh cookie travel cross-origin.

Request logging in dev format.

The refresh token is rotated on every use. Calling refresh writes a new hash onto the same session document and re-issues the cookie, so a stolen refresh token dies at the next legitimate refresh. 03 — Data model

Project holds now. Deployment holds history.

That split is the single most important structural decision in the codebase. Without a separate Deployment entity there is no build history, no per-commit detail, no replayable logs, and no way to tell a finished build from a running one.

Five collections. Both hashes are SHA-256; no secret is stored in plaintext.

Three fields worth stopping on

Project.name

Constrained to /^[a-z0-9-]+$/ because it becomes the DNS label in <name>.<domain>. Unique globally, not per owner, since subdomains are a global namespace.

Deployment.owner

Denormalized from the project so both the REST check and the socket room check are one indexed query with no populate.

Deployment.steps

Pre-populated by a schema default, so all five rows exist as pending the moment the record is created. The stepper renders before the worker even wakes up.

Step status has five values, not three: pending running success failed skipped

04 — Signup flow

Registration deliberately returns no token
sequenceDiagram autonumber participant C as Client participant API as API server participant DB as MongoDB participant G as Gmail OAuth2 C->>API: POST /auth/register API->>DB: findOne username OR email API->>API: bcrypt.hash(password, salt 10) API->>DB: create User (verified false) API->>DB: create Otp { sha256(otp), TTL 300s } API->>G: send the 6-digit code API-->>C: 201 — no token C->>API: POST /auth/verify-email API->>DB: findOne Otp by { sha256(otp), email } API->>DB: User.verified = true API->>DB: deleteMany Otp for user API->>DB: create Session (sha256 of refresh token) API-->>C: 200 + accessToken + httpOnly cookie
Verification is the only door into an authenticated state for a new account.

Login rejects an unverified user with 401, and registration hands back nothing. So handleVerifyEmail creates the session and returns an access token itself. Without that, a user would verify their email and then be bounced to a login form.

The OTP is hashed too

Only sha256(otp) is stored. The document carries expires: 300 on createdAt, so MongoDB's TTL monitor deletes it about five minutes later with no application code involved.

05 — Create a project

Created and queued in one request
sequenceDiagram autonumber participant C as Client participant API as API server participant DB as MongoDB participant R as Redis C->>API: POST /api/project { name, repoUrl, branch } API->>DB: findOne Project by name Note over API: 409 if taken — name is globally unique API->>API: webhookSecret = randomBytes(20).hex API->>DB: create Project (QUEUED, repoUrl minus .git) API->>DB: create Deployment (QUEUED, 5 pending steps) API->>R: LPUSH build-queue API-->>C: 201 { project, deployment }
  • The .git suffix is stripped at write time, so webhook lookups later have one canonical form to match.
  • Status is QUEUED, never IDLE. IDLE is the schema default but the create path skips it, because a project always builds the moment it exists.
  • A failed enqueue fails both records. Nothing is left sitting in QUEUED waiting for a job that was never posted.

The deployment comes back in the response so the client can navigate straight into a live build view without a second request.

06 — Build pipeline

One worker, one job, five steps
API                 Redis list "build-queue"                 Worker
 |                                                             |
 +-- LPUSH ---------> [ job ]                                   |
 |                        |<--------------- BRPOP (timeout 0) --+ blocks

BRPOP with a timeout of 0 blocks indefinitely, so the worker burns no CPU while idle and there is no polling interval to tune. LPUSH at the head plus BRPOP at the tail makes the list FIFO. The loop handles one job at a time, globally — not one per project. That is precisely why redeploy returns 409 on a concurrent build: two jobs would race on the same workspace directory.

#StepServiceWhat actually happens
1CLONEsimple-gitwipe and recreate workspace/<id>, then git clone --branch <b> --depth 1
2DOCKERFILEdocker.servicean existing Dockerfile is left alone; otherwise detect the runtime and write one
3BUILDdocker.servicedocker build --platform=linux/amd64 --progress=plain, 10-minute timeout
4PUSHecr.serviceauth token, docker login --password-stdin, ensure repo, tag, push
5DEPLOYecs + albregister a task definition, then branch on ALB_ENABLED

currentStep is tracked in a plain variable across the whole try block, so a throw anywhere marks exactly the right step failed before the deployment goes FAILED.

Runtime detection

A fixed precedence chain, first match wins.

Probe fileBase imageStart command
Dockerfile—untouched, generation skipped entirely
package.jsonnode:18-alpinenpm start, else node <main>
requirements.txtpython:3.12-slimpython <entry>, or Django's runserver
go.modgolang:1.20-alpine to alpine./main, multi-stage, CGO_ENABLED=0
none—throws; the build fails at step 2

Python entry-point detection is the only heuristic. One .py file wins outright; otherwise each is scanned for a __main__ block, a .run(, uvicorn, Flask(__name__) or FastAPI(), falling back to main.py.

Port 8080 is a three-file contract

Every generated Dockerfile ends with ENV PORT=8080 and EXPOSE 8080, because CONTAINER_PORT in the ALB service is 8080 and the ECS task definition maps that port. Change one and all three must move.

Three deliberate flags

  • --platform=linux/amd64 is not optional on Apple Silicon. Fargate runs x86, and an arm64 image pushes fine then fails to start.
  • --progress=plain forces line-based output. BuildKit's default emits TTY redraw sequences that capture badly into a log record.
  • docker build writes progress to stderr under normal operation, so the worker labels that stream stdout anyway rather than painting a healthy build red.

On the push side, the ECR password is piped through --password-stdin and never passed as an argument, so it cannot appear in the process list. That login is also the one Docker call made without a log sink, because it prints a credential-storage warning that has no business in a user-visible build log.

07 — Two deploy paths

A supervised service, or a one-shot task

The task definition is identical either way: Fargate, awsvpc, 256 CPU units, 512 MB, a container named user-app-container on port 8080, logging to /ecs/vercel-clone. That container name is not arbitrary — CreateService names a container and port pair in its loadBalancers block, and a mismatch is rejected with an opaque validation error.

ALB off

RunTask with a public IP. Nothing supervises it, nothing restarts it, the IP changes every deploy, and liveUrl stays null. The UI shows "URL pending".

ALB on

An ECS service behind a shared load balancer. Supervised, restarted on crash, rolled without downtime, reachable at a stable subdomain.

Running without a load balancer is supported, not broken

An ALB bills roughly $16 a month from the moment it exists. Working without one has to stay a first-class path, which is why the whole feature sits behind one flag.

Why a service and not a task

A service registers the task's private IP into the target group on start and deregisters it on stop, automatically. Doing that by hand would break the first time a task restarted with a new IP.

Both ensureTargetGroup and ensureListenerRule are idempotent, because a redeploy calls them again. The rule function has a third branch that is easy to miss and matters most: if a rule for the host exists but forwards to a different target group, it is repointed. Without that, recreating a target group leaves the old rule holding a dead ARN and every request 503s.

Priorities 1 through 9 are reserved for future platform rules. Project rules start at 10, and findFreePriority reuses gaps left by deleted projects rather than marching toward the 100-rule listener ceiling.

The distinction this enforces

"ECS started the task" and "the app is reachable" are different claims, and only the second justifies READY. A container that boots but never binds its port looks perfectly healthy from ECS's side while the ALB serves 503. Target health is the real signal.

The three ARNs are written to the project before the health wait, not after, so a build that times out still leaves enough state behind for deletion to clean up what it provisioned. Progress lines are deduplicated against the previous summary, since at a 10-second cadence a repeated identical line would bury everything interesting.

08 — Log streaming

Realtime and durability have different latency budgets
flowchart LR D["docker build
stdout / stderr chunk"] --> L["logger.log()"] L --> A["stripAnsi

immediately, per line"] BUF -->|50 lines or 1s| M[("MongoDB

One path optimizes for latency, the other for cost. They are deliberately not the same path.

Docker output is chatty. Writing each line to MongoDB individually would be hundreds of round trips per build. So publishing is immediate and per-line, while Mongo writes are batched at whichever comes first of 1 second or 50 lines, capped at the last 2000 lines by $slice.

flush() chains onto a promise rather than firing concurrently, so overlapping callers cannot interleave batches out of order, and it is awaitable so the worker's finally block can guarantee the tail of a log is never lost.

Three event types, one channel

typeExtra fieldsDrives
logline, streamthe terminal panel
stepstep, statusthe five-stage stepper and its per-step timers
statusstatus, liveUrl, errorMessagebadges, the live link, query invalidation
Flush before publishing a terminal status

status() updates the deployment, mirrors the status onto the project, await flush() if terminal, and only then publishes. Clients refetch when they see READY or FAILED, so anything still in the buffer would be missed. It is also why the worker logs "Deployment complete." before calling status("READY").

The socket layer does three things

1 Handshake auth

Verifies handshake.auth.token with the same secret as the REST middleware and pins socket.userId. Invalid tokens are rejected at connect.

2 Ownership-checked rooms

subscribe:project matches the id and the owner before joining. Without it any logged-in user could read anyone's build logs.

3 The Redis bridge

A duplicate() connection, because ioredis rejects ordinary commands on a subscriber. The lpush/brpop client cannot be reused.

ANSI stripping happens server-side, so the database stays clean and the frontend needs no ANSI library at all. The splitter also handles a bare carriage return, which is how progress bars overwrite themselves in place.

Replay is what makes a mid-build refresh work. GET /api/deployment/:id is the only endpoint that returns logs; the frontend calls it on mount to seed state, then lets the socket take over. A build that finished last week still renders its complete stepper and output.

09 — GitHub webhook

Authenticated by HMAC instead of JWT
sequenceDiagram autonumber participant GH as GitHub participant API as API server participant DB as MongoDB participant R as Redis GH->>API: POST /api/webhook/github Note over GH,API: x-github-event · x-hub-signature-256 API->>API: ping or non-push → 200 and stop API->>DB: findOne Project { repoUrl in [url, url.git], branch } Note over API,DB: no match → 404 API->>API: HMAC-SHA256 over req.rawBody with project.webhookSecret Note over API: mismatch → 401 API->>DB: Project.status = QUEUED API->>DB: create Deployment (WEBHOOK + commit metadata) API->>R: LPUSH build-queue API-->>GH: 200 { project_id, deploymentId }
Raw bytes, not JSON

The signature is computed over req.rawBody. Re-serializing the parsed object can reorder keys or change unicode escaping and fail a legitimate signature.

Timing-safe compare

timingSafeEqual throws on a length mismatch, so lengths are checked first and an early false returned.

Project first, then signature

The secret is per-project and lives on the document. There is no global webhook secret to check against.

Both URL forms

Matched with and without .git, since users paste both. The branch must match too, so a push to an untracked branch is a 404.

Non-push events return 200, not 400

GitHub disables webhooks that repeatedly return errors, and "I do not care about this event" is not a failure.

10 — Delete and teardown

AWS mandates the order

A target group in use by a service, or referenced by a rule, cannot be deleted.

flowchart TB A["deleteECSService(force: true)"] --> B["wait 8 seconds
DRAIN_WAIT_MS"] B --> C["deleteListenerRuleByArn"] C --> D["deleteTargetGroupByArn"] D --> E["Project.deleteOne()"] E --> F["Deployment.deleteMany({ project })"] A -.->|catch| W["push a warning
never throw"] C -.->|catch| W D -.->|catch| W W -.-> E
Every AWS failure becomes a warning in the response. None of them block the Mongo delete.
The asymmetry that drives this design

A leaked listener rule can be removed by hand from the console. A project that cannot be deleted is stuck in the user's dashboard forever. So the AWS teardown never throws, and the warnings are returned rather than swallowed, because each leaked rule consumes one of the listener's 100 slots.

  • Both delete helpers swallow their not-found exceptions, so a half-finished earlier attempt cannot permanently block a retry.
  • The 8-second drain only runs if a service actually existed.
  • A project with no AWS resources at all returns from the guard clause immediately, making zero AWS calls.
  • The controller reads before deleting rather than using findOneAndDelete: the ARNs live on the document, and the project must stay visible during the drain while its container is still serving traffic.

11 — State, timing and failure

One state machine, kept in lockstep
stateDiagram-v2 [*] --> QUEUED: create · redeploy · webhook push QUEUED --> BUILDING: worker picks up the job BUILDING --> DEPLOYING: ECR push done (ALB path only) BUILDING --> READY: no-ALB path DEPLOYING --> READY: target passes health checks BUILDING --> FAILED: clone, dockerfile, build or push threw DEPLOYING --> FAILED: rollback or 3-minute timeout QUEUED --> FAILED: enqueue failed, or watchdog READY --> QUEUED: next push or redeploy FAILED --> QUEUED: next push or redeploy

The 3-minute health timeout sits comfortably inside the 15-minute watchdog window, so a health failure surfaces as a real diagnosable error rather than being swept up by the watchdog.

The watchdog

cleanStaleBuilds() runs once at worker startup and then every 15 minutes, force-failing anything untouched past the cutoff. It casts a wider net over deployments (QUEUED included) than projects, because a job can be enqueued and then stranded if the worker dies before picking it up. Both must be cleaned — resetting only the project would leave a deployment spinning forever in the UI.

12 — Config and the feature gate

Eleven variables, or the server does not boot

config.js throws at import time if MONGO_URI, PORT, JWT_SECRET, the four GOOGLE_* or the four core AWS_* variables are missing. Failing at boot is deliberate: a missing secret surfaces immediately instead of as a confusing 500 hours later. FRONTEND_URL, AWS_REGION and AWS_ECS_CLUSTER_NAME are defaulted instead of required, and REDIS_URL is read straight from process.env inside config/redis.js. 

ALB_REQUIRED_KEYS = ["AWS_VPC_ID", "AWS_ALB_LISTENER_ARN", "PLATFORM_DOMAIN"]
config.ALB_ENABLED = ALB_REQUIRED_KEYS.every(present)

One flag for the whole feature, so no caller re-checks three variables and drifts out of sync about which ones matter. The warning logic is the interesting part.

StateBehavior
all three presentsilent — subdomain routing active
all three absentsilent — deploys work, liveUrl stays null
one or two presentconsole.warn at boot

Only the half-configured case warns, because that is the one that surfaces later as an opaque AWS validation error from inside a build. Fully off is a supported configuration, not a broken one. alb.service.js defends independently with assertAlbEnabled() at the top of every AWS-touching function.

13 — Sharp edges

Known gaps, none of them breaking normal use
1 · liveUrl is https, the listener is http

buildLiveUrl returns https://, while its own doc comment says the opposite and ALB-SETUP.md provisions only an HTTP:80 listener. As written, every liveUrl handed to the UI points at a scheme nothing is listening on until a :443 listener with a certificate exists.

2 · ecsServiceArn holds a name, not an ARN

The worker writes serviceName into it and deleteECSService correctly expects a name. Only the field name is misleading.

3 · models/user.js is dead code

A near-duplicate of user.model.js that nothing imports. Both call mongoose.model('User'), so importing the wrong one would raise OverwriteModelError.
